# ChelEVSE Architecture

> Status: v1 shipped. This document is the design source of truth for the system as built. It covers the topology, the Firestore contract, runtime flows, the bridge and PWA internals, deployment and test topology, and the known gaps. Behavioural details live in `README.md`, `pi/README.md` and `docs/VALIDATION.md`; this document explains how the pieces fit and why.

## 1. Goals, scope and constraints

### Goals

- Move OpenEVSE charger status and control off the home LAN and onto a phone, reliably.
- Keep the moving parts small: no self-run backend, no inbound connections to the house, no third-party control broker.
- Keep the data contract explicit enough that a native client could replace the PWA without touching the bridge.

### Non-goals

- Multi-tenant operation, fleet management, or a public API.
- Supplier tariff import, standing charges, export rates, or automatic plan optimisation.
- Interval-level metering accuracy beyond the approximations documented below.

### Constraints

- **Firebase is the only public surface.** Firestore carries data, Hosting serves the PWA, Auth gates access. The bridge initiates outbound HTTPS to Firebase and LAN connections to the charger; the only inbound listener is the LAN-only Mosquitto broker for the charger.
- **The Firestore schema evolves additively.** No migration framework and no document version field; new fields are optional and absent means the old behaviour.
- **Local wall clock is authoritative** for charger schedules, rate windows, daily history and session display. Sessions and server timestamps are UTC instants; conversion happens at the edges.
- **The PWA has no build step.** Plain ES modules, no framework, no bundler.
- **Single-household assumptions** are acceptable: one bridge instance, one charger, a small allowlist. Where that assumption is load-bearing it is called out in §11.

## 2. System topology

```
┌────────────────┐   LAN HTTP      ┌────────────────────┐   outbound HTTPS   ┌─────────────────────────┐
│ OpenEVSE       │◄───────────────►│ Raspberry Pi       │───────────────────►│ Firebase                │
│ WiFi module    │   LAN MQTT      │ bridge agent       │   Admin SDK        │ Firestore  (data)       │
│ (ESP32)        │◄───────────────►│ + Mosquitto broker │   status writes    │ Hosting    (PWA)        │
└────────────────┘   status/control└────────────────────┘   command watch    │ Auth       (Google)     │
                                                                              └────────────┬────────────┘
                                                                                           │ HTTPS / WSS
                                                                                ┌──────────▼───────────┐
                                                                                │ Phone / desktop PWA  │
                                                                                │ Firebase Auth sign-in│
                                                                                └──────────────────────┘
```

Trust boundaries:

- **Firebase** is internet-reachable and enforces access with Auth + Firestore rules.
- **The home LAN** is trusted. The charger's HTTP API may be unauthenticated or Basic-auth; the Mosquitto listener is LAN-only and authenticated.
- **The Pi** holds the Admin service-account key, so it is the most privileged component. The bridge initiates Firebase and charger connections; the only inbound listener is Mosquitto on the LAN. Nothing outside the LAN can connect in.

Data flow, in one line: charger → bridge → Firestore → PWA, and PWA → Firestore → bridge → charger. The bridge is the only writer of charger state and the only component that talks to the charger.

## 4. Data model — Firestore is the API

### Principles

- **One document shape per concern.** The bridge writes charger state and derived history with the Admin SDK (bypassing rules by design). The PWA writes only the three client-owned documents: `settings/current`, `schedule/current`, `commands/*` (plus its own `fcmTokens/*`).
- **No schema migrations.** Optional fields are added; absent/empty means the previous behaviour. `settings/current.rates` is the worked example: absent = One rate.
- **Read-time derivation.** Costs, schedule state and config presentation are computed when rendered, never persisted. Changing a rate schedule immediately re-prices history.
- **Curated status, raw config.** `status/current` is a fixed, unit-normalised field set. `status/config` is the charger's `/config` with secrets redacted; it is replaced wholesale, not merged.

### Rate schedule (`settings/current.rates`)

```js
{
  rate: 0.245,                 // stored One-rate price; ignored when rates exist
  currency: "GBP",
  rates: [                     // optional; absent/empty = One rate
    { id: "base", rate: 0.30, days: [0,1,2,3,4,5,6], start: "00:00", end: "00:00", months: null },
    { id: "peak", rate: 0.32, days: [1,2,3,4,5],     start: "16:00", end: "19:00", months: [11,12,1,2] }
  ]
}
```

- `days`: `0` = Monday … `6` = Sunday, matching the charge schedule and `DAY_NAMES`. `Date#getDay()` is converted with `(getDay() + 6) % 7`.
- `start`/`end`: local `HH:MM`, half-open `[start, end)`. `end <= start` wraps past midnight; `start === end` covers the whole day.
- `months`: `null` = all year, or an inclusive list `1–12`. A range may wrap the year (Nov → Feb = 11, 12, 1, 2).
- `from`/`to` (optional): `"MM-DD"` bounds of a day-precision season, inclusive and recurring annually. The editor presents these as native date inputs against a 2024 reference year; only the month and day are stored. Both or neither must be valid; `from > to` wraps the year (`10-15` → `04-15`), `from === to` is one day, and `02-29` is a real date (`02-30` is not). When both are valid they outrank `months`, which is then only the derived compatibility hint a save writes; a one-sided or unreal pair makes the row invalid, so it is dropped from costing instead of falling back to stale months. Every reader in the editor derives the scope and month hint from the dates, so a date row with a missing or stale hint still loads; the hint is written for older readers that only understand months.
- **Base and override:** an all-day, every-day row (`days: [0..6]`, `start === end`) is a season **base**: it prices every hour of its scope unless a daily window overrides it. A day-restricted all-day row is an override, not a base. No schema key marks either one; the shape is the marker. A base plus daily windows is the supported model. Two bases covering the same date are rejected, as are two daily windows that can both match one instant; a base and an override may overlap because the override simply wins for its hours.
- **Resolution:** override → season base → **0**. `settings.rate` is used only when `rates` is absent/empty. Dates outside every season and hours a season does not price cost 0.00; the editor and history flag them instead of inventing a fallback.
- **Post-midnight attribution:** a window's after-midnight hours belong to the day the window started. A Monday 22:00–06:00 window covers Tuesday 00:00–05:59; a season ending 15 September prices 16 September 00:00–05:59 with 15 September's rate; a December-only window covers 1 January 00:00–05:59.
- **Overlap rejection:** windows that can both match one local instant are rejected by the editor. Validation compares annual date sets on a 366-slot leap ring (month-day positions, with 29 February as a real slot) and the four main/tail combinations, so adjacent seasons sharing a month but no day do not collide, a December wrap and January's early hours do, and 29 February is exact.
- **Payload:** a month row is `{id, rate, days, start, end, months}` unchanged; a date row appends `from`/`to` after `months`, whose value is derived from the dates (`10-15` → `04-15` = `[10,11,12,1,2,3,4]`). Old clients ignore the dates, read the derived months and over-apply at month edges.
- **Legacy overlaps:** a document written outside the editor may still contain same-tier overlaps. Matching is deterministic: a matching override wins over a base, and within each tier the **last matching row in list order wins**. A base plus override is not a legacy collision but the model. The editor blocks the next save until same-tier overlaps are resolved, and payload order is preserved so grouping never changes legacy semantics.
- **Limits:** ≤ 24 windows. `web/js/rates.js` owns normalization, matching, overlap detection and interval costing; `web/js/settings.js` owns form validation, normalization/dirty comparison and the save payload.

### Cost semantics

Costs are presentation values, computed on every render from the current settings and never stored:

- **One rate:** `kWh × rate`, exactly the pre-schedule behaviour. Once any row exists, gaps are 0.00 and the stored rate is ignored.
- **Live session:** the interval is `[updated_at − elapsed, updated_at]`, anchored to the status write. It is shown only while the charger is actually charging (`state_label === "charging"` and `charger_online !== false`). Paused/ready snapshots hide the figure instead of sliding it; a stale cache-only charging snapshot keeps the figure frozen at its own interval; an offline marker hides it. If any slice of the interval has no base/window price, that slice is 0.00 and the line adds **understates cost** on its own warning line.
- **History session:** `costForIntervals` when the document carries a usable `intervals` list that also adds up to its `wh` within `max(250 Wh, 2%)` — one price per charging block, so energy drawn in a cheap window stays cheap even with an idle gap inside the plug-in span — else `costForSession` over `started_at…ended_at`, pro-rating `wh` uniformly across the rate boundaries. The reconciliation is the money guard: a restart-orphaned or reset-overshot list would otherwise price the wrong energy in either direction. All-or-nothing: an unusable or divergent list falls back to the aggregate, a trusted list with an unpriceable interval hides the figure, and an unusable `wh` keeps the legacy behaviour. Flat (one-rate) configs ignore intervals entirely, byte-identically to before.
- **Aggregate daily/period cost:** `kWh × rate` under a flat rate (`aggregateCostLabel`, byte-identical to the pre-schedule output); under a schedule, priced on every render from the day documents' hourly buckets — each bucket over its own wall-clock hour (`costForInterval`), a day as the sum of its buckets, a Year month as the sum of its days. A day with energy but no hourly detail (recorded before hourly capture began) is unpriceable: a range mixing such days with priced ones shows the priced-only total beside a note disclosing the gap, a range whose energy is entirely unpriceable hides the figure, and zero-energy days are fully priced at 0.00 — an empty range is $0.00, not a partial one. Everything is computed on read from `settings/current`; nothing is ever written to `history/*`. A history banner also flags any 0.00 moments and links back to settings. Approximation (accepted): buckets are hour-granular and their spans are local-midnight + h·3600 s, so a DST-shifted day prices its 24 buckets against the 23 or 25 real hours it has, and a period total may differ slightly from summing its per-session costs.
- **Approximation (accepted):** inside one charging interval the stored value is a single `wh`, so the energy is assumed to have been drawn at constant power; each slice between rate boundaries gets its duration's share. Ramps within a window are therefore priced slightly off. Sessions recorded before charging intervals, sessions whose intervals were never measured, and sessions whose intervals do not reconcile with their `wh` still pro-rate across the plug-in span, which can be off by the rate difference across an idle gap. Interval bounds are observed, not invented: when a wall-clock step inverts a pair it is re-anchored from the interval's `CLOCK_BOOTTIME` span, so the priced duration is still the time actually charged — though the derived end is the pre-step open plus that span, so it can post-date the record's `ended_at`; an inverted pair with no measured span is absent rather than guessed; and a step that does not invert the pair is kept as observed, so that interval's span is off by the step.

### Schedule (`schedule/current`) and commands

- The charge schedule is enforced by the charger's firmware, not the bridge. The bridge validates and mirrors it; a missing or malformed document leaves the firmware untouched (never an implicit clear), while `enabled: false` or an empty rule list clears it.
- The bridge converts each rule to two firmware events: an `active` event at the start and a `disabled` event at the end. Overnight ends shift to the next firmware day. A digest skips unchanged schedules; a 300 s reconcile re-posts after a firmware reset.
- The bridge drops a later rule whose window overlaps or touches an earlier one (first rule wins). The web editor validates field shapes but does not detect those cross-rule collisions, so the bridge is the effective validator.
- Commands are a typed whitelist: `pause` (stop), `resume` (clear override → auto), `set_current` (6–48 A), and `rapi` (the advanced escape hatch; must match `^[$][A-Za-z0-9]{1,2}([ ].*)?$`, ≤ 32 chars). Only `pending` creates are accepted; the bridge alone settles them.
- Transport is chosen by the bridge, not the client: MQTT when connected, subscribed and ready; HTTP otherwise. A publish accepted by MQTT is never re-applied over HTTP. The command doc records the transport that carried a request (`"mqtt"` or `"http"`), and none when rejected before send.

## 5. Bridge agent (`pi/`)

Python 3 service under systemd (`Restart=always`, `User=root`), installed by rsync to `/opt/chelevse` with a venv. It authenticates to Firebase with a service-account key from `private/`. Five loops run as daemon threads (status, config, settings (the charger-address refresh), schedule, and the optional MQTT status apply), the command loop runs on the main thread, and support threads handle FCM delivery and paho's network loop:

### Write budget (issue #96)

Every successful Firestore write is counted by kind (`status`, `history`,
`session`, `config`, `command`, `health`, `fcm` — deletes bill as writes) in a
process-local rolling 24 h counter threaded from `run()` through every write
site. It surfaces as an hourly journal summary, as `writes_24h` /
`writes_by_kind` merged into `status/health` on that document's existing
transition writes (so the counter itself costs no writes), as a tripwire
warning at 50 % of the quota, and as a distinct line when a write fails with
the SDK's `RetryError`-wrapped 429 — which otherwise reads like a timeout.
The policy's budget: ~320 writes/day with no charging, ~1,180 at the real
14 h/day charging workload, ~2,020 worst case (rate-limit saturated) — well
inside the free tier's 20,000/day. Reads are not the binding constraint (the
5 s command poll's 17,280 reads/day fits the 50,000 free, and slower polls
would make button presses feel slower); batching would not help either, since
Firestore bills per document written. Per-state table and rationale:
`pi/README.md` → _Write budget and counter_.

### Status ingestion

- HTTP and MQTT converge on `parse_status`: milliamps → amps, tenths °C → °C, absent sensors → `null`, `uint64` sentinels coerced, curated whitelist. Both feed the same state machine, history and session logic.
- MQTT snapshots are debounced (~500 ms), seeded from a `/status` reply, and only run the state machine once complete. Ordering guards (`mqtt_mark`, arrival generations, seed-if-current) prevent a late HTTP reconcile from rewinding a newer MQTT apply.
- MQTT is opt-in (`MQTT_ENABLED=false` by default). When enabled, the broker is Mosquitto on the Pi, LAN-only and authenticated; the bridge subscribes to `<topic>/#` and the firmware announce topic (`openevse/announce/#`, retained state + Last Will). HTTP remains the reconciler and the fallback.
- When HTTP is the status source (or MQTT is not ready), failed polls merge `{charger_online: false, updated_at: SERVER_TIMESTAMP}` and keep the last values. Under a ready MQTT source, offline requires two consecutive failed reconciles with no snapshot; a late snapshot cancels the outage. The app distinguishes bridge staleness from charger offline with `freshnessState`, whose bounds anticipate the bridge's planned write cadences (#93): an online snapshot that says charging is stale after 150 s (2.5× the future 60 s heartbeat) and renders a "Not updating" banner, any other online snapshot after 12 min (2× the future 300 s idle heartbeat plus margin) with the bridge banner, while an offline marker takes precedence with no age test.

### Commands and watchdog

- MQTT commands: `override/set` for pause/resume/set-current (confirmed against the retained `override` doc, with a status fallback), `rapi/in`/`rapi/out` for RAPI (serialised; replies carry no correlation id, so a short quarantine retires timed-out replies). HTTP commands use `/override` and `/rapi`.
- The watchdog probes after consecutive `/status` failures. HTTP answering → `POST /restart`; HTTP unreachable but MQTT connected/subscribed and not Last-Will-disconnected → publish on `<topic>/restart`; neither → alert only. Charging guard, cooldown and hourly cap apply across transports; the transition into unhealthy sends one push and recovery sends another.
- Session tracking merges pause/resume across a plug-in (see §4). History is accumulated from `total_energy` deltas; a failed Firestore write keeps the baseline and retries the next tick.

### Configuration and secrets

- `private/bridge.env` supplies `CHARGER_HOST`, `FIREBASE_SERVICE_ACCOUNT`, loop intervals, MQTT settings and optional charger Basic auth. Real environment variables override the file. `CHARGER_HOST` is only the **bootstrap** address: `settings/current.charger_host`, when the app has set a valid value, overrides it at startup and at runtime, with no restart (the startup log names the address and its source).
- Redaction covers credential/config keys before `status/config` is written. The service account bypasses rules; it must never reach the web app or the repo.
- OTA/firmware flashing is **not implemented** in the bridge. Firmware updates are a manual operation against the charger; `status/config` exposes the firmware version for reference. (See §11 for the documentation drift on this point.)

## 6. Web PWA (`web/`)

### Shell and lifecycle

- One `index.html` with five mutually exclusive screens: `booting`, `boot-error`, `signin`, `noaccess`, and `app`. `app` holds a five-tab `tablist` and five `tabpanel` sections (Status, History, Schedule, Config, Advanced). Hash routing selects the tab; `aria-selected` and roving focus follow the APG tabs pattern.
- Boot: dynamic Firebase SDK init → screen `init*` wiring → tab bar → auth subscription. A missing/invalid `web/firebase-config.js` produces `boot-error`; a missing grant produces `noaccess` with a sign-out control.
- `app.js` owns auth fan-out, data subscriptions, the status ticker lifecycle, lazy history load, Config-time notification refresh, and push toast display. Sign-out closes the store, resets every screen and releases the push token (bounded to 3 s); a revoked grant only releases the token for `no-access`.
- `closeApp` is the teardown boundary: subscriptions stop, screen state resets, `activeUser` clears.

### Store and screens

- `store.js` owns `status/current`, `status/config`, `settings/current`, `schedule/current` (snapshot with metadata; settings also carries the snapshot's cache provenance and an error callback), `commands` (recent + pending windows), `history/{date}` reads (one `documentId()` range per period, plus the Day period's single-document `getDoc`) and `sessions` (paged: 20 per page, newest first, continuing after the previous page's last document snapshot via `startAfter`, with an optional `started_at` range for the month browse — the range filters the ordered field, so the automatic single-field index serves it; `fetchSessions` returns the last snapshot beside the docs as the next page's cursor), and writes for settings, schedule, commands and FCM tokens.
- **Status** keeps the latest snapshot, schedule and settings; a 1 s ticker runs only while the Status tab is selected; the pulse is gated by `liveCharging`; command feedback lasts 5 min; Stop freezes the clock until a genuinely new write.
- **Settings** holds draft rows, a confirmed baseline and an optional pending snapshot. Flags: loaded/dirty/saving/waiting/saved/error, plus a failed-read flag. Save is held until the server has answered the `settings/current` read — including the answer that reports no document — because until then there is no baseline and the whole-document write would delete the stored rate plan and charger address; a cached snapshot that reports no document is only the local cache answering before the server, so it does not open the gate (a cached snapshot that carries the document does, since it holds the stored values). A draft typed before that snapshot lands is completed from it, keeping every value the owner typed. While the hold is up the card says `Loading your settings…`, or the offline copy when the browser reports no connection; a listener error keeps the gate closed and says the read failed. Offline saves are refused before the write; a timeout enters "waiting" with late reconciliation; a failure rolls back to the newest server snapshot. The card also carries the **Charger address** (`charger_host`): validated as a bare IPv4 literal or hostname, carried through the whole-document write (which only runs after that snapshot), so a rate-only save never deletes it, and omitted from the payload when blank so clearing reverts the bridge to `CHARGER_HOST`. The rate editor has two derived modes: **One rate** (no rows) and **Seasons & time-of-use**. Switching to Seasons seeds one visible **current-month** season at the flat rate and focuses **Base rate**; the rest of the year stays an uncovered gap the owner covers with its inline **Cover the rest of the year** action (or **Fill gaps** / **Add a season**). Switching to One rate confirms the loss, reuses a single All-year base's price when possible, and drops the rows. Every season opens on a visible **Season dates** block above **Base rate** and **Daily windows (optional)**: native **Starts**/**Ends** pickers use 2024 as a reference year while only `MM-DD` is stored, **All year** clears the dates, **Edit dates** on a collapsed header expands and focuses the block, and **Advanced: month ranges** appears only for a legacy non-contiguous month scope (or a malformed month scope that has to be repaired) — dates are the only normal scope editor. A new season seeds the largest uncovered date range (All-year when no base exists and the year is covered) and focuses Base rate; legacy month scopes show derived dates, and non-contiguous months open the month editor. A season base is an all-day every-day row; daily windows are overrides, and a base plus windows is valid. Uncovered dates are 0.00 with **Fill N gaps** (empty bases, focused first) and a plan summary gap count; a base-less season offers **Add base rate** only when no other base already overlaps its dates. Duplicate copies a season into its free complement. Date commits repaint in place when no merge or split occurs; structural edits rebuild on the next task and restore the `data-field` control. Add a base is withheld at the row cap and when it would collide with an existing base. The stored shape and matching are unchanged.

- **Schedule** separates confirmed vs draft, supports optimistic queued writes, a queued-from-snapshot flag, unconfirmed-save handling, discard baseline reads and remote notices. A schedule can be disabled even if its rules are invalid.
- **History** uses one-shot reads: the selected period's range (Week 7 days, Month 30 days, Year 12 months — at most 366 daily documents in one `documentId()` query), the Day period's single `history/{today}` document (a cached miss rejects, so it reads as that period's offline copy), and recent sessions (not listeners). It tracks provenance separately, never paints cached/stale data as current, and rechecks midnight while open: every read path ends in one shared guard, so a Day read in flight across midnight is re-entered with today's ids. Day draws 24 hourly buckets from the document's `hours` map through the same slot geometry and hit test as every other period; a day with a nonzero `kwh` but no usable `hours` is a **no intraday detail** message (its total stays in the summary) instead of 24 zero bars. Every period's summary and each bar also carry an estimated $: flat-rate totals stay `aggregateCostLabel`'s byte-identical path, while under a schedule the series points' pricing inputs (an hour's day, a day's `hours` map, a month's day documents) price each bucket through `js/cost.js` — re-priced on read whenever settings change, never stored. A range that mixes days with and without hourly detail shows the priced-only total plus a disclosing note; the Day period's no-intraday day keeps its cost hidden with the panel copy explaining why. The four-option segment re-reads history only; the sessions list keeps its own read. The sessions list pages through the archive on demand: a **Show more** control appends the next page (started after the last shown document snapshot) without duplicates, hidden when a server-answered short page concludes the archive — so a small archive never shows it — and disabled while a page is in flight; a failed page keeps the rendered list with the section note reporting, and the control stays usable for a retry. A native month picker narrows the read to that month's `started_at` range (paging within the month works the same way), with a **Recent** reset back to the newest-first view; a failed month read keeps the previous view's list on screen, and Refresh re-reads the current view's first page. Only the shown sessions are counted (no Firestore count aggregation). The paging rules are pure (`nextSessionsView`/`sessionsControls` in the History screen), so accumulation, exhaustion and view adoption are pinned without a DOM. Period descriptors and series derivation are pure (`js/history.js`), so bar geometry and the hit test follow the rendered point count and the descriptor's `source`, not a period-id branch.
- **Advanced** requires a per-visit confirmation gate and shows a 20-entry RAPI scrollback.
- **Notifications** is a card state machine (`checking/unsupported/no-vapid/denied/granted/default`) backed by the DOM-free token lifecycle.

### Settings save state machine

The settings editor is the most stateful screen. The flow is:

1. A draft is compared to the confirmed snapshot as parsed values, not text.
2. A save validates the document plus the rate rows; invalid input paints field errors and focuses the first problem.
3. Offline → refuse before incrementing the write generation.
4. Write → `settleWrite`; a timeout re-enables the form in a "waiting" state while the write continues.
5. Success adopts the sent values and the latest remote echo; failure rolls back to the newest confirmed snapshot; a late settlement is generation-guarded so the first outcome wins.

Any future editor (including #58) must preserve these semantics.

### Offline, service worker and push

- `web/sw.js` is a plain service worker with no Firebase SDK. `CACHE` is currently `chelevse-v56`; `SHELL` lists every runtime `web/js/**` module plus the root assets. `test/web/sw-shell.test.js` fails if a module is missing, duplicated, or if `CACHE` is malformed.
- Fetch is cache-first for same-origin GETs, except `firebase-config.js`, which is deliberately network-only. Navigation falls back to `index.html`; other failures return 503. Cross-origin/Firebase requests always go to the network.
- Install precaches the shell and `skipWaiting`; activate deletes old caches and `clients.claim`; the page reloads once on `controllerchange` only if a controller already existed. **Any shell change must bump `CACHE`**, or existing clients keep the old modules.
- Firestore uses its persistent cache with a multi-tab manager and an in-memory fallback. A cold reload still needs the network for the SDK and `firebase-config.js`.
- Push: FCM sends a notification-only message; the worker shows the system notification or posts `chelevse-push` to a visible page for exactly one in-app toast. The page dedupes against the SDK's defensive `onMessage` within 5 s. `pushsubscriptionchange` asks open pages to re-acquire and re-save the token; a token rotation therefore recovers without user action. The bridge prunes invalid tokens.

## 7. Firebase platform and security

### Auth and allowlist

- Firebase Auth with Google Sign-In. Anyone can authenticate; data access requires a `users/{uid}` grant with `allowed == true` **and** a verified email.
- `private/acl.txt` (one email per line) is the owner-managed allowlist. `pi/acl.py` syncs it to grant docs with the Admin SDK; `--prune` removes grants and their FCM tokens. A person must sign in once before they can be granted (the auth user must exist).

### Rules boundaries

| Path                                             | Rules                                                                                                                         |
| ------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------- |
| `users/{uid}`                                    | read own only; write `false`                                                                                                  |
| `status/{doc}`, `history/{day}`, `sessions/{id}` | read allowlisted; write `false`                                                                                               |
| `schedule/{doc}`                                 | allowlisted write; exact keys `enabled`, `rules`; bool/list/≤20; per-rule shape re-validated by the bridge                    |
| `settings/{doc}`                                 | allowlisted write; `rate` 0–5, `currency` 1–8, optional `rates` list ≤24; per-window shape and overlaps validated client-side |
| `fcmTokens/{token}`                              | read false; create/update own uid with exact keys; delete own doc even after grant revocation                                 |
| `commands/{cmd}`                                 | create allowlisted and `pending`, with one of the four typed shapes; update/delete false                                      |

Rules cannot iterate a list, and per-element checks on the 20/24-entry arrays exceed the 1,000-expression evaluation limit. The design therefore uses **container-only guards** for `schedule.rules` and `settings.rates`, with the app validating before write and the bridge re-validating the schedule it receives. This is a deliberate trade-off, not an oversight.

### Hosting and indexes

- Hosting serves `web/` with an SPA rewrite to `index.html`. Every path is served `no-cache, max-age=0, must-revalidate`; there is no per-file split. `Cross-Origin-Opener-Policy: same-origin-allow-popups` supports popup sign-in; COEP is not set.
- One composite index: `commands` by `type` ascending, `created_at` descending, for the Advanced scrollback. The pending-command query and recent-command window use single-field indexes.
- The custom domain `charge.chelydra.dev` points at the `chelevse-906d4` Hosting site; Auth authorized domains must include the Firebase domains and the custom domain.

## 8. Deployment and operations

### Project and credentials

- Firebase project **`chelevse`** (`.firebaserc` default). Never deploy ChelEVSE to `boxedturtle-30096`.
- Bridge key: `private/service-account.json` (Cloud Datastore User, Firebase Auth Viewer, FCM Admin).
- Deploy key: `private/chelevse-deploy-service-account.json` (Firebase Admin, Datastore Index Admin). The README/DEPLOY examples still name `private/deploy-service-account.json`; the operator convention and the file actually present are the explicit `chelevse-` name.
- Web config: `web/firebase-config.js`, gitignored.

### Deploy pipeline

`npm run deploy:*` scripts each run `scripts/check-firebase-project.mjs` first. The guard resolves the target from `FIREBASE_PROJECT` or `.firebaserc`, resolves the key from `GOOGLE_APPLICATION_CREDENTIALS` or `private/service-account.json`, and blocks a mismatch. **Caveat:** with no key present the guard warns and exits 0, so a deploy is only truly guarded when credentials resolve.

- `deploy:dry-run` compiles rules and validates the release without publishing.
- Rules first, then indexes (wait for the index to build), then hosting. `npm run deploy` does all three.
- Deploy from `main` after the merge, never from a feature branch; no `--force`. Fix forward on a branch.

### Pi deployment

`sudo bash pi/install.sh` is the only supported path. It rsyncs `pi/` (with `--delete`) and `private/` (without `--delete`) to `/opt/chelevse`, builds/updates the venv, installs the unit and restarts the service. It is idempotent. Do not hand-edit `/opt/chelevse`.

### Failure modes

| Failure              | Behaviour                                                                                                                                                                                                                                                          |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Pi offline           | Status writes stop; the PWA flags it once the state-aware bound passes (~150 s if the last snapshot says charging, ~12 min otherwise — sized for the write policy's 60 s / 300 s heartbeats; see §5)                                                               |
| Charger unreachable  | Bridge retries, writes `charger_online: false` immediately (the outage edge sits outside the write policy's rate limit), distinguishes charger-offline from bridge-offline; watchdog restarts over HTTP or MQTT and alerts when neither path works                 |
| MQTT broker down     | Bridge logs one transition, resumes 10 s HTTP polling, records `source: "http"`; the charger publishes into the void without affecting charging                                                                                                                    |
| Firebase blip        | SDKs reconnect; bridge retries failed writes next tick; history keeps failed deltas in the accumulator and retries them on the next flush point (hour rollover / session close / the charging interval / shutdown), still attributed to their observed hours (#94) |
| PWA offline          | Loaded app works from the Firestore cache and SW shell; cold reload needs the network (SDK/config are network-only)                                                                                                                                                |
| Stale deployed shell | Shell is cache-first; a shell change must bump `CACHE`; an open tab keeps old modules until reload                                                                                                                                                                 |
| Index building       | Advanced reports `failed-precondition` until Firestore reports the index ready                                                                                                                                                                                     |

## 10. Key decisions

| Decision                                      | Rationale                                                                                                                      | Consequence                                                                                                                                                                                     |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Serverless Firebase over a custom backend     | Firestore listeners give realtime updates with no server code; free tier is ample; a native client can reuse the contract      | Rules are the security boundary; client validation is UX, not enforcement                                                                                                                       |
| Raspberry Pi bridge                           | The ESP32 firmware has no Firebase client; a LAN bridge covers status **and** control without a cloud broker                   | One always-on host; service-account key on the Pi; no inbound ports                                                                                                                             |
| MQTT-first status and commands, HTTP fallback | The firmware publishes per-field topics and accepts native commands; latency drops to seconds and polling drops to a reconcile | Broker on the Pi; `MQTT_ENABLED=false` is the rollback; HTTP remains for config, plan, commissioning and counters                                                                               |
| Firestore as the API                          | Both bridge and PWA speak the same documents; no RPC surface to version                                                        | Additive schema evolution; no migrations; document shapes are the contract                                                                                                                      |
| Two explicit modes, no fallback               | The owner sees One rate or a priced season plan; gaps and unpriced hours are explicit 0.00, never a stale rate                 | `rate` remains stored but is ignored when rows exist; flat payloads stay byte-identical; history/status flag unpriced time                                                                      |
| Read-time pricing                             | Changing a tariff must re-price history immediately; no stale persisted costs                                                  | Costs are approximate inside a charging interval (constant-power assumption), and pro-rated across the plug-in span for records without intervals or whose intervals do not reconcile with `wh` |
| Local wall clock                              | Tariffs and schedules are expressed in the owner's local time, including DST                                                   | All boundary logic uses local `Date` helpers; day numbering is explicit (`0=Mon`)                                                                                                               |
| Presentation-only TOU refresh                 | Seasons can be made legible without a schema migration (#58, shipped in #63)                                                   | Grouping/periods are derived from month scopes; window order and semantics are preserved                                                                                                        |
| No build step / plain ES modules              | The app is small, auditable, and deployable as static files                                                                    | Manual module wiring; SW shell list must be maintained; cache bumps are mandatory                                                                                                               |

## 11. Known gaps and future work

- **TOU/seasonality editor (#58):** shipped in #63, superseded by the unified base/override editor in #76. Season-first periods, immediate month apply, own/effective coverage tables with named sibling periods, a draft-live checker, and now explicit uncovered-date/hour warnings at 0.00. Residual: the settings form's `addEventListener('submit')` binding is covered only by the external harness, not an in-repo DOM test.
- **Date-precision seasons and season rates (#65):** shipped in #75. Dates are the primary visible scope: native Starts/Ends pickers with a 2024 reference year, All year, a repeat hint, and Edit dates on a collapsed header; legacy month scopes keep **Advanced: month ranges**.
- **Unified season pricing (#76):** shipped in PR #75 (this change), closing #76. Two explicit modes (One rate / Seasons & time-of-use), no fallback: a season is dates + a base + optional daily overrides, gaps cost 0.00 with Fill gaps/Add base warnings, and the checker/history/status name uncovered dates, unpriced hours and unpriced live time. No new schema field: the all-day, every-day row is the base.
- **OTA is not implemented.** The bridge has no firmware upload/version/rollback path. `ARCHITECTURE.md` and `docs/DEPLOY.md` historically described OTA as an HTTP responsibility; treat firmware updates as manual until the code exists.
- **Deploy guard is weak without a key:** `check-firebase-project.mjs` warns and exits 0 when no credentials resolve. Deploy commands in README/DEPLOY also use a key filename that differs from the operator convention.
- **Rules test coverage:** add read-authorization tests for `status`, `history`, `sessions` and `users`; the core data paths are currently unexercised.
- **Command hardening:** rules do not require `created_at` or reject extra keys; the bridge treats a missing/malformed `created_at` as not stale, so a crafted pending doc can bypass the 10-minute sweep and sit indefinitely. There is no command claim/lease, so two bridge instances would double-apply.
- **Settings listener error handling:** `settings/current` has no error callback; a permission/backend failure leaves the card silently empty instead of showing an error.
- **Single-bridge assumptions:** session upsert is read-then-write (not transactional), schedule sync uses a digest, and watchdog counters are process-local. These are acceptable for one Pi but not for HA.
- **Bridge runs as root.** The unit is `User=root`; a dedicated service user with access to `private/` and the charger would reduce blast radius.
- **History retention:** `history/*` and `sessions/*` grow without pruning; the UI reads the selected period (at most 366 days for a Year view) and the sessions archive 20 at a time — "Show more" pages deeper on demand, and the month picker reads any one month's range.
- **Docs drift:** `docs/DEPLOY.md` still mentions OTA; README/DEPLOY deploy-key filenames differ from `AGENTS.md`; `firestore.rules` still carries a stale comment about schedule validation landing later.

## 12. Glossary

| Term                | Meaning                                                                                                                                                                  |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **One rate**        | `settings/current.rate`; the flat price when `rates` is absent/empty                                                                                                     |
| **Rate row**        | One entry in `settings/current.rates`: price + weekday set + local time range + month set or date bounds                                                                 |
| **Base rate**       | An all-day, every-day row (`days: 0..6`, `start === end`); prices every hour of its season unless an override wins                                                       |
| **Daily window**    | A rate row that is not a base; overrides the base for its days and local time range                                                                                      |
| **Period / season** | A presentation grouping of rows sharing a month or date scope; not persisted                                                                                             |
| **Live cost**       | Scheduled cost for the current session, anchored to `status.updated_at − elapsed` and shown only while charging                                                          |
| **Aggregate cost**  | Daily/period cost from one kWh total; hidden when a schedule exists                                                                                                      |
| **MQTT source**     | The bridge's optional event-driven status/command path; HTTP is the reconciler and fallback                                                                              |
| **Transport**       | `mqtt` or `http`, recorded on a command when the bridge actually sent it                                                                                                 |
| **Bridge stale**    | No status write past the state-aware threshold: 150 s while charging, 12 min idle (≈2× the heartbeats the write policy of #93 will adopt); distinct from charger offline |
| **Grant**           | `users/{uid}` doc with `allowed: true`; the allowlist primitive                                                                                                          |
| **SHELL**           | The service-worker precache list; any change requires a `CACHE` bump                                                                                                     |
